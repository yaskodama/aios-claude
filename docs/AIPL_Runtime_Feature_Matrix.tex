\section*{Overview}

AIPL (Actor-based Intelligent Parallel Language, formerly AIPL)
has grown into a \textbf{seven-runtime project}.  This document
provides a side-by-side comparison of every language and
infrastructure feature across all implementations, grounded in
source surveys.

\paragraph{Legend.}
\Yes\ = full support, \Part\ = partial, \No\ = not supported,
\NA\ = not applicable.

\paragraph{Column abbreviations in matrices below.}
\textbf{Py-A}~=~Python annotated, \textbf{Py-I}~=~Python inferred,
\textbf{OCaml}, \textbf{JS-O}~=~JS via OCaml backend,
\textbf{JS-B}~=~JS in browser, \textbf{JS-N}~=~JS in Node server,
\textbf{C}~=~aipl2c codegen.

\paragraph{Inheritance relationships.}

\begin{itemize}[leftmargin=*,itemsep=0pt]
  \item \textbf{JS-OCaml} is a thin HTTP client over the OCaml
    backend, so its feature set inherits OCaml's (plus the new
    \texttt{/api/typecheck} endpoint).
  \item \textbf{JS-Node} wraps the same browser-abcl parser /
    type-checker / interpreter inside a Node.js HTTP server.
    Runtime feature set therefore mirrors JS-Browser.
  \item \textbf{Python (inferred)} imports parser, interpreter, AI,
    remote, and dashboard from \texttt{../python-aipl/}.  All
    \emph{runtime} features match Python (annotated); only the
    \emph{static type-checker} layer differs (full
    Hindley-Milner instead of Phase 11+ annotation-driven).
\end{itemize}

\subsection*{Three concurrency tiers}

\begin{itemize}[leftmargin=*,itemsep=0pt]
  \item \textbf{1:1 OS thread / process} (Python, OCaml, C, C-SDL2,
    Xinu, C$\to$Python, C$\to$Prolog): each actor is a kernel-scheduled thread.
    Simple mental model; blocking I/O in one actor doesn't stall
    others.  Scales to $\sim$100--1000 actors before kernel
    overhead dominates.
  \item \textbf{M:N lightweight} (Pony, Erlang, Go): actors are
    scheduled by the language runtime onto a small pool of OS
    threads.  Scales to $\sim 10^{5}$--$10^{7}$ actors.
    Blocking syscalls in one actor may stall its scheduler unless
    the runtime intercepts them (Erlang's BEAM intercepts; Go's
    runtime intercepts via \texttt{netpoll}; Pony's runtime
    requires non-blocking idioms).
  \item \textbf{Cooperative event loop} (browser-abcl,
    node-aipl-server): single OS thread; mailboxes are drained
    turn-by-turn through \texttt{setTimeout(0)} re-entry into the
    event loop.  No real parallelism, but message-level
    interleaving is preserved.  A long synchronous computation in
    one actor \emph{will} stall all others --- by design, since
    this is the only concurrency model the browser DOM allows.
\end{itemize}

\subsection*{Cross-cutting implication}

The AIPL programming model (\texttt{send} / \texttt{now} /
\texttt{future} / \texttt{await}) is preserved across all three
tiers --- the choice of target picks a point on the cost/scale
curve without changing the program text.  The same \texttt{.abcl}
file:
\begin{itemize}[leftmargin=*,itemsep=0pt]
  \item runs $\sim$1000 actors fine on Python / OCaml / C
    (OS-thread tier);
  \item scales to millions of actors on Erlang / Go / Pony codegen;
  \item runs in a browser sandbox via JS-Browser at the cost of
    single-threaded execution.
\end{itemize}

\section*{Key observations}

\subsection*{Python (annotated) is the most feature-complete runtime}

Of the 30 surveyed features, Python (annotated) ticks roughly 28.
It owns the full Phase 11--17 stack (channels, linear types, owned
fields, effects, structured concurrency, transient casts), method
injection, dynamic compile, persistent actor state, full AI
integration (streaming + multimodal images), and Pillow-backed
image I/O (PNG / JPEG / GIF / WebP).

\subsection*{Python (inferred) --- Python's HM-typed twin}

Runtime features match Python (annotated) exactly because the
interpreter is shared.  The trade is on the static side: the Phase
11+ annotation-driven checks are replaced with a Hindley-Milner
inference pass.  Inferred types cross-verified against OCaml: on
shared samples (\texttt{Hello.abcl}, \texttt{counter.abcl}) the two
runtimes produce identical type schemes.

\subsection*{OCaml --- feature parity with Python on the core}

After the OCaml feature catch-up, the runtime supports
\textbf{method injection} (\texttt{add\_method}/\texttt{remove\_method}),
\textbf{dynamic compile} (\texttt{compile()} + \texttt{spawn()}),
\textbf{top-level functions} with \textbf{generics}
(\texttt{function id(x: T) -> T}), \textbf{type annotations},
\textbf{records \& tuples}, \textbf{sized arrays}
(\texttt{var x[N][M]}), and \textbf{text/image file I/O} (PPM
backend for images).  Phase 11+ effect / linear / owned / transient
features still only exist as \texttt{.abcl} design-document samples
\textemdash{} not statically enforced.  Solid \texttt{become} /
\texttt{select} / WebSocket (built into \texttt{web\_gateway.ml})
and HTTP remote actor calls (\texttt{send}\,/\,\texttt{now}\,/\,\texttt{future},
error-tolerant) with \textbf{HMAC-signed traffic}
(\texttt{ABCL\_REMOTE\_SECRET} 環境変数, 純 OCaml HMAC-SHA256 in
\texttt{src/hmac\_sha256.ml}, Python / C 版とワイヤ互換).

\textsuperscript{d} \small OCaml の remote client (\texttt{src/remote\_client.ml}) は \texttt{send} (fire-and-forget) / \texttt{now} (同期 reply) / \texttt{future} (並列 + await) の 3 形式すべてをサポート。ECONNREFUSED / timeout は stderr に記録され、呼び出し側のアクターは生存する。エンドツーエンド検証は \texttt{src/test\_remote\_actor.sh} (9/9)。JS-O は OCaml バックエンド経由でこれを継承する。

\textsuperscript{e} \small 純 OCaml HMAC-SHA256 (\texttt{src/hmac\_sha256.ml}, RFC 6234 / 4231 テストベクタで verify) を sender と receiver の両側で使う。\texttt{ABCL\_REMOTE\_SECRET} が両端でセットされたとき、全リクエストに \texttt{X-ABCL-Sig: <hex>} が付与される。\texttt{web\_gateway.ml} の \texttt{verify\_hmac\_or\_reject} は不一致なら 401 を返す。\texttt{python-aipl/aipl\_remote.py} と C ランタイムにワイヤ互換。以前は受信側が \texttt{openssl dgst} をサブプロセス起動していたが、インプロセスの純 OCaml 版に置換 (リクエスト毎の fork 排除)。

\subsection*{JS-OCaml $\approx$ OCaml}

A thin HTTP client (\texttt{src/app.js} etc.) over the OCaml
backend exposed by \texttt{web\_gateway.ml}.  Every OCaml-side
feature \textemdash{} method injection, dynamic compile, top-level
functions, generics, type annotations, file \& image I/O
\textemdash{} is reachable via \texttt{/api/repl} from a browser or
\texttt{curl}.  The OCaml-specific differentiator is the
\texttt{/api/typecheck} JSON endpoint.

\subsection*{JS-Browser --- minimal in-browser engine}

Basic actor model plus flow-sensitive type inference.
Recently picked up \textbf{sized arrays} (\texttt{var x[N]}) and
\textbf{text \& image file I/O} (host-injected \texttt{fs}; throws
in browsers).  No \texttt{become}, no channels, no remote, no
method injection.  AI integration exists but is mock-only.

\subsection*{JS-Node $\approx$ JS-Browser + fs}

Wraps the browser-abcl runtime inside a Node.js HTTP server
(\texttt{src/node-aipl-server/server.mjs}); auto-injects Node's
\texttt{fs} so the text \& image I/O builtins are functional.
Exposes \texttt{/api/typecheck} and \texttt{/api/run} for headless
use.  Same flow-sensitive type inference as browser-abcl.

\subsection*{C codegen --- broadest target diversity}

\texttt{become} and \texttt{select} remain codegen-unsupported
(emit \texttt{/* unsupported */}), but the codegen inherits OCaml's
HMAC, SSE, and AI governance, and offers \textbf{9 backends} from
one front-end:
\begin{itemize}\itemsep0pt
  \item C + pthread (default)
  \item \textbf{C + LLVM / clang} (\texttt{--llvm}: adds
    \texttt{\_\_attribute\_\_((hot/cold))} + headers for
    \texttt{clang -emit-llvm})
  \item \textbf{C + OpenMP} (\texttt{--openmp}: \texttt{\#pragma omp
    parallel for} spawn loop + \texttt{\#pragma omp atomic} counter)
  \item C + SDL2 (GUI demos)
  \item Xinu / Python / Pony / Erlang / Go / SWI-Prolog
\end{itemize}
Fields, parameters, and locals are specialised to native C types
via HM inference + per-class field-type registry.

\section*{Method injection \textemdash{} now in three runtime families}

Both Python variants and the OCaml runtime (with JS-OCaml piggy-backing
on it) implement mutable method dispatch tables with runtime
\texttt{add\_method} / \texttt{remove\_method} / \texttt{methods\_of}.
\texttt{browser-abcl} and \texttt{node-aipl-server} still lack even
\texttt{become} and rely on the unchanging method table baked at
parse time.

\section*{Type inference cross-verification}

For shared samples (\texttt{abclc/Hello.abcl},
\texttt{abclc/counter.abcl}), the three HM-based runtimes
(\textbf{OCaml}, \textbf{Python-inferred}, \textbf{C}) produce
identical inferred types:

\begin{verbatim}
Hello:   count : float
         init  : (int) -> unit
         greet : () -> unit
         inc   : () -> unit

Counter: count : float
         inc   : () -> unit
         dec   : (float) -> unit    <- monomorphized via call site
\end{verbatim}

The flow-sensitive variants (\textbf{JS-Browser},
\textbf{JS-Node}) reach the same answers on shared samples within
the limits of their algorithm — field types match, but method
signature schemes are not produced the same way.

\section*{Phase 11+ implementation gap}

The full Phase 11--17 stack is implemented only in Python
(annotated).  This represents AIPL's language-evolution frontier;
Python (annotated) serves as the research runtime.  Python
(inferred) keeps the runtime side but trades the static checks for
HM-style polymorphic inference --- a different research axis
(declarative typing vs. annotated capabilities).
