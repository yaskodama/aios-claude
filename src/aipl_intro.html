Actor-based Interactive Programming Language

AIPL とは
—— アクターで書く並行言語

AIPL は，独自に設計したアクターベースの並行プログラミング言語である。 すべてを「メールボックスを持つアクター」とそのメッセージ交換で表し，同一言語のまま OCaml・Python・ブラウザで動き，AIPL→C 変換で実機 Embedded-Xinu 上でも走る。 Hindley–Milner の型推論を備え，web_listen ひとつで Xinu 互換の HTTP アクターゲートウェイになる。

01 アクターモデル

すべては「アクター」とメッセージ

アクターは自分専用のメールボックスを持ち，届いたメッセージを 1 通ずつ順に処理する独立した実行単位。 状態は各アクターに閉じており，共有メモリのロックは不要。通信は 3 種類。

図: アクターとは何か。各アクター(A・B)は自分専用のメールボックスと，外部から直接 read/write できない状態(state)を持ち，method() で処理して reply する。他アクターへは send msg(x) の非同期メッセージだけで働きかける。状態を変えられるのはメッセージだけで，各アクターは独立スレッドで直列処理するため，ロック無しで競合しない。（出典: Keynote「AIPL — 型付きAIエージェント言語」）

send
非同期送信。相手のメールボックスへ入れて即座に戻る（fire-and-forget）。
now
同期送信。相手が reply(v) するまで待ち，その値を受け取る。
future
先物。すぐ future を返し，await(f) で後から値を取り出す。
reply
メソッド内で呼び出し元へ返信する。now/future の待ち手を解く。

02 文法の要点

  
クラス・メソッド・フィールド

  
アクターは class で定義する。var がフィールド（状態），
  method がメッセージハンドラ。制御構文は while … do { }・
  if … else，自由関数は function。

  

    
class / method
アクター定義とハンドラ。new Foo(a,b) は method init(a,b) を呼ぶ。

      
var
フィールド（各アクターの状態）。メソッド内で代入・更新できる。

    
send self.m()
自分自身へ非同期送信。ループ的な処理を段階に分ける定石。

      
配列
array_empty / array_push / array_get / array_len で集合・列を扱う。

Slide 2 · 例1 PingPong

      
2つのアクターがメッセージを投げ合うだけの最小例

      
    
        
  • Pinger と Ponger が ping/pong を往復させる。スレッド生成もロックもコードに現れない。
    • 
        
  • send は非同期＝送った側は待たずに次へ進む。往復はメッセージが順に配送されることで進む。
    • 
        
  • sender はそのメッセージの送り主を指す組み込み。返信先を引数で持ち歩く必要がない。
    • 
        
  • 往復は無限に続く。止めるのは実行系側の仕事で，CLI では --max-msgs 12，下のデモでは ■ Stop。
    • 
      

      

        
      

      
緑の球が 1 通のメッセージ。send した瞬間に送り主を離れ，届いた時点で受け手のハンドラが動く
      （光っている側が実行中＝print が出た瞬間）。ソースは無改変で，
      待ち時間を持たない往復を目で追えるよう，配送間隔の下限だけをホスト側（実行系の外）で 600ms にしている。

      
上のデモが実行している ABCL ソース — abclc/PingPong.abcl と同一AIPL

Slide 3 · 例2 4つの線分の回転

      
線分1本 = アクター1つ。4本が同時に回る

      
    
        
  • 4本の線分がそれぞれ独立したアクター。中心・角度・色はそのアクターだけの状態なので，共有変数も排他制御も要らない。
    • 
        
  • send self.rotate() ＝ 自分自身へ送り返すことがアニメーションループになる。while ループではなく1メッセージ = 1フレーム。
    • 
        
  • 4つの rotate が並行に回るが，各自が自分の線を消して描き直すだけなので衝突しない。
    • 
        
  • 描画は call で外へ出す。この 1 本のソースが実行系ごとに姿を変える：ブラウザは canvas_line，
        デスクトップ GUI 版（abclc/Rotate4Lines.abcl）は sdl_line_c，Xinu 実機・VM 版は line。
    • 
      

      

        
      

      
4 本が同時に回る。各アクターは自分の中心と角度しか持たず，互いに一切同期していない。
      色は実行系がアクターごとに割り当てたもの。

Slide 4 · 例3 食事する哲学者

      
フォークもアクター。ロック無しで排他と待ちを書く

      
    
        
  • フォーク5本・哲学者5人＝10アクター。フォークを取る＝take を送って fork_granted を待つこと。ロックもセマフォも無い。
    • 
        
  • 取れないとき Fork はブロックしない。送り主を waiter に覚えておき，release のとき次の人へそのまま渡す＝待ち行列がアクターの状態として書ける。
    • 
        
  • デッドロック回避は資源順序付け。全員が低い番号のフォークから取る（lowFork → highFork）。p0 の隣は fork0 と fork4 で，ここだけ「左の前に右」を取ることになり，この非対称性が循環待ちを断つ。
    • 
        
  • call は描画フック（philo_state / fork_held / fork_free）。下のデモは，この直下のソースを AIPL 処理系(JS 実装)がその場で構文解析して動かしている。サーバは不要。

▶ Run / ■ Stop で制御できる。円は哲学者（灰=THINK / 黄=HUNGRY / 緑=EAT），棒はフォークで，
      保持者の色になり保持者を指す。下がその実行ソース（デモが実際に parse して走らせている文字列そのもの）。

04 分散 — Xinu 互換 HTTP と「移動」

  
web_listen ひとつでアクターがネットワークに出る

  
web_expose("info", info) でアクターを名前付きで公開し，
  web_listen(PORT) で HTTP アクターゲートウェイ（POST /api/json/call）を起こす。
  これは実機 Embedded-Xinu（rpi3/4/5）が話す配線と同一で，同じ .abcl を実機へ載せても動く。
  端末をまたぐエージェントの「移動」は，now remote(host,"actor").method(args) による
  ネイティブ同期リモート送信で表す。

  
端末の起動 + 情報拡散エージェントの 1 ホップ移動AIPL



  
この仕組みで「各避難者 = 1 台の soft-Xinu ノード（4 エージェント）」が構成され，
  通信範囲 50\,m の MANET メッシュ上を情報拡散エージェントがブロードキャストして火災情報を伝える
  （ポータルの MANET / MANET(2) カード）。






  
05 型システム

  
Hindley–Milner の型推論（型推論クリーン）

  
型注釈をほとんど書かずとも，Hindley–Milner 型推論がフィールド・メソッドの型を導く。
  「型推論クリーン」とは，この推論が型エラー 0 で通る状態を指す
  （OCaml ランタイムでは load 時に検査）。数値は int/float を混在でき，
  演算子はオーバーロードで解決される。実機 Xinu 向けには AIPL→C 変換（JIT）でネイティブ実行する。

07 Xinu × メッシュ × TinyML

  
Xinu を接続してメッシュを構築し，その上に分散知能をのせる

  
各端末 = 1 台の Xinu が通信範囲で相互接続すると MANET メッシュになる（ポータルの
  MANET / MANET(2) カード）。この各 Xinu ノードに TinyML（認識のための小型 AI）をのせ，
  AIPL（論理判断）・AICE（分散 Actor 実行）・Xinu（リアルタイム制御）と組み合わせて，
  推論結果をメッシュへ流して協調する分散知能をつくる——これが新しい研究の方向である
  （tinyml_aipl_xinu_guide.pdf）。

  

    
層役割内容

    
TinyML認識 (perception)センサ／画像から小型 NN で推論（例: person=0.94）。量子化・TF Lite Micro・MCUNet で MCU/エッジ上に収める。

    
AIPL論理判断LogicActor が規則を適用（「人を検出し，かつ危険領域にいるなら警告」）。認識の確率を論理へつなぐ。

    
AICE分散 Actor 実行SensorActor → TinyMLActor → LogicActor → Motor/DroneActor をメッシュ上のノードへ配置・協調。

    
Xinuリアルタイム制御デバイスドライバ・通信・アクター配置を担い，推論結果でモータ／ドローン等を実時間制御。

  

  
Xinu で TinyML を使う三つの方式

  

    
方式推論の場所Xinu の役割

    
A. Raspberry Pi GatewayPi 側で TinyML 推論（最も現実的な第一歩）推論要求の送出・結果受信・それに基づく Actor 制御／配置判断。

    
B. 小型 C 推論を移植量子化した小型モデルを C 推論で Xinu 上に直接推論そのものを実機で実行（Python/TF はそのまま載せない）。

    
C. 外部 AI モジュール外部モジュールが推論デバイスドライバと Actor 制御に専念。

  

  
📄 資料PDF: TinyML入門 — AIPL・AICE・Xinu 連携（tinyml_aipl_xinu_guide.pdf）→

  
メッシュとの結節点（共同設計）: MCUNet がモデルと推論エンジンを共同設計するように，
  AIPL/AICE は「Actor 構造・配置・通信・TinyML モデル」を共同設計できる。すなわち
  CameraActor / TinyMLActor をどの Xinu ノードに置くか，推論結果をどの粒度で Mesh へ流すかを
  コンパイラまたは Runtime が決める研究へ発展する（TinyML Actor の移動 (migration) 実験を含む）。
  行き着く先は Physical AI・XOS・分散 Robot OS。（出典: tinyml_aipl_xinu_guide.pdf）
